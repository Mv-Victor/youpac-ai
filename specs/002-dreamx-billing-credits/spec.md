# Feature Specification: DreamX 站内计费与兑换码系统

**Feature Branch**: `002-dreamx-billing-credits`  
**Created**: 2026-04-07  
**Status**: Draft  
**Input**: User description: "在001-dreamx-video-workflow分支基础上，为现在的DreamX新增一个站内计费系统。初期简单起见，管理员可以通过离线脚本运行批量获取兑换码，用户获取单个兑换码之后，进入dashboard，侧边栏左侧原来是有setting的，现在模仿setting界面建立一个兑换码系统，输入兑换码即可兑换生成项目次数。兑换码有三种，一种是体验版本（30积分），一种是vip（150积分），一种是svip（500积分）。统计每个项目节点中的交互按钮（如重试、确认等），凡是有需要LLM参与进行调用的（或者点击之后会引发一次LLM调用的），都标识上消耗N点积分的图标tag（如果有图片参与，则3张为附加1点积分，不满足3张也是，以这种规则计算单次交互消耗积分）。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 用户兑换积分 (Priority: P1)

已注册用户在 Dashboard 侧边栏找到「兑换码」入口，输入从管理员处获取的兑换码，成功后账户积分余额立即增加，页面显示新的积分余额。

**Why this priority**: 积分是整个计费系统的基础货币，没有积分兑换则无法使用任何付费功能，属于核心流程。

**Independent Test**: 用户在兑换码页面输入有效兑换码，提交后页面显示积分增加及最新余额，即可验证完整闭环。

**Acceptance Scenarios**:

1. **Given** 用户已登录且持有一个未使用的体验版兑换码，**When** 在兑换码页面输入该码并点击确认，**Then** 账户积分增加 30 点，页面显示兑换成功并展示最新余额。
2. **Given** 用户已登录且持有一个 VIP 兑换码，**When** 在兑换码页面输入并确认，**Then** 账户积分增加 150 点。
3. **Given** 用户已登录且持有一个 SVIP 兑换码，**When** 在兑换码页面输入并确认，**Then** 账户积分增加 500 点。
4. **Given** 用户已登录，**When** 输入已被使用过的兑换码并确认，**Then** 系统提示该兑换码已使用，积分余额不变。
5. **Given** 用户已登录，**When** 输入不存在或格式错误的兑换码并确认，**Then** 系统提示兑换码无效，积分余额不变。
6. **Given** 用户已登录，**When** 尝试使用他人已兑换的兑换码，**Then** 系统拒绝兑换并提示已使用。

---

### User Story 2 - 积分消耗与项目节点交互 (Priority: P2)

用户在 DreamX 项目工作流中，每个需要 LLM 参与的节点交互按钮（如重试、确认、生成等）均显示本次操作的预计积分消耗标签，用户点击后系统扣减对应积分，积分不足时操作被阻止。

**Why this priority**: 积分消耗机制是计费系统的核心价值体现，使用户清晰了解成本并保障服务可持续。

**Independent Test**: 在已有项目工作流中，找到一个 LLM 调用按钮，确认其显示积分标签，点击后查看积分余额减少对应数值即可验证。

**Acceptance Scenarios**:

1. **Given** 用户打开任意 DreamX 项目，**When** 查看节点中需要 LLM 调用的交互按钮，**Then** 按钮上显示该操作的积分消耗标签（如「2 积分」）。
2. **Given** 用户积分充足，**When** 点击标记了积分消耗的按钮，**Then** 操作正常执行，账户积分扣减对应数值。
3. **Given** 节点操作不含图片输入，**When** 计算该操作积分消耗，**Then** 消耗积分为该节点的基础积分值。
4. **Given** 节点操作含 1 张或 2 张图片（不足 3 张），**When** 计算积分消耗，**Then** 在基础积分之上额外附加 1 点积分。
5. **Given** 节点操作含 3 张图片，**When** 计算积分消耗，**Then** 在基础积分之上额外附加 1 点积分（每满 3 张计 1 点附加，不足 3 张也计 1 点）。
6. **Given** 节点操作含 6 张图片，**When** 计算积分消耗，**Then** 额外附加 2 点积分。
7. **Given** 用户积分余额不足以完成某操作，**When** 查看该节点的 LLM 调用按钮，**Then** 按钮显示为 disabled 状态，hover 时展示 tooltip 提示积分不足并引导前往兑换码页面。

### User Story 3 - 管理员批量生成兑换码 (Priority: P3)

管理员在本地运行离线脚本，传入数量和类型参数，脚本生成指定数量的兑换码并输出到文件，管理员将兑换码分发给用户。

**Why this priority**: 管理员工具是供给侧流程，先于用户兑换存在，但属于后台操作不影响用户侧核心体验。

**Independent Test**: 管理员运行脚本生成 10 个 VIP 兑换码，脚本输出包含 10 条唯一兑换码的文件，可在系统中验证这些兑换码有效即可完成测试。

**Acceptance Scenarios**:

1. **Given** 管理员在有权限的终端环境，**When** 运行脚本并指定类型为「体验版」、数量为 N，**Then** 脚本生成 N 个唯一的体验版兑换码（对应 30 积分）并输出到文件。
2. **Given** 管理员运行脚本生成 VIP 兑换码，**When** 生成完成，**Then** 每个兑换码对应 150 积分，且所有兑换码全局唯一不重复。
3. **Given** 管理员运行脚本生成 SVIP 兑换码，**When** 生成完成，**Then** 每个兑换码对应 500 积分，且所有兑换码全局唯一不重复。
4. **Given** 管理员生成的兑换码，**When** 同一用户尝试使用同一兑换码两次，**Then** 第二次使用被拒绝。

---

### User Story 5 - 查看积分流水 (Priority: P4)

用户在兑换码页面可查看简单的积分变动记录列表，包含兑换和消耗两类流水，了解积分来源与去向。

**Why this priority**: 流水可见性帮助用户核对积分变动，增加系统可信度。

**Independent Test**: 兑换一次兑换码后，流水列表出现一条兑换记录，变动积分数值与兑换码类型对应。

**Acceptance Scenarios**:

1. **Given** 用户已登录，**When** 进入兑换码页面，**Then** 页面展示积分流水列表（变动类型、积分数量、时间）。
2. **Given** 用户成功兑换兑换码，**When** 兑换完成，**Then** 流水列表新增一条兑换记录。
3. **Given** 用户触发 LLM 调用并扣减积分，**When** 扣减完成，**Then** 流水列表新增一条消耗记录。

---



用户在 Dashboard 侧边栏或兑换码页面随时查看当前积分余额，了解剩余可用积分。

**Why this priority**: 积分余额可见性是用户决策的基础，属于辅助但必要的功能。

**Independent Test**: 在兑换码页面可见当前积分余额数值，兑换后数值实时更新。

**Acceptance Scenarios**:

1. **Given** 用户已登录，**When** 进入兑换码页面，**Then** 页面显示当前积分余额。

### Edge Cases

- 用户积分余额为 0 或不足以支付某操作时，该操作按钮显示为 disabled 状态，hover 时展示 tooltip 提示积分不足并引导前往兑换码页面（不可点击，不触发服务端调用）。
- 兑换码字符大小写是否敏感（默认不敏感，兑换时统一转换为大写校验）。
- 同一兑换码并发兑换（两个请求同时提交同一兑换码）需防止重复兑换，系统只允许一次成功。
- 脚本生成兑换码时若网络不可用（离线模式），生成的码需在数据库同步后才能使用。
- 节点图片数为 0 时不计附加积分。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须支持三种兑换码类型：体验版（兑换 30 积分）、VIP（兑换 150 积分）、SVIP（兑换 500 积分）。
- **FR-002**: 每个兑换码只能被使用一次，使用后标记为已使用，不可再次兑换。
- **FR-003**: 用户必须能够在 Dashboard 侧边栏通过「兑换码」入口（仿 Setting 界面布局）进入兑换码页面。
- **FR-004**: 兑换码页面必须显示用户当前积分余额，并在兑换成功后实时更新。
- **FR-005**: 兑换码输入框提交后系统必须校验兑换码的有效性（存在性、未使用状态），无效时返回明确的错误提示；输入时自动转为大写，支持带或不带连字符格式（`XXXXXXXXXXXXXXXX` 或 `XXXX-XXXX-XXXX-XXXX`）。
- **FR-006**: 管理员必须能够通过本地离线脚本批量生成指定类型和数量的兑换码，生成结果输出到文件。
- **FR-007**: 脚本生成的所有兑换码必须全局唯一。
- **FR-008**: 项目工作流中每个触发 LLM 调用的交互按钮（重试、确认、生成等）必须显示该操作的积分消耗标签。
- **FR-009**: 积分消耗计算规则：基础积分（从 Convex `NodeCreditConfig` 表动态读取，管理员可配置）+ 图片附加积分（ceil(图片数量 / 3) 点，0 张图片时附加 0 点）。
- **FR-010**: 用户积分余额不足时，对应按钮显示为 disabled 状态，hover 时展示 tooltip 提示积分不足并引导用户前往兑换码页面；不触发服务端调用。
- **FR-011**: 积分扣减时序：先发起 LLM 调用，调用成功（请求被接受）后再原子性扣减积分；若 LLM 调用失败则不扣减积分。
- **FR-012**: 兑换码字符校验不区分大小写。
- **FR-013**: 兑换码页面必须展示用户积分流水列表，包含变动类型（兑换/消耗）、积分数量、发生时间，按时间倒序排列。

### Key Entities

- **兑换码（RedeemCode）**: 唯一标识码、类型（体验版/VIP/SVIP）、对应积分数值、创建时间、使用状态（未使用/已使用）、使用者用户 ID、使用时间。
- **用户积分账户（UserCredits）**: 用户 ID、当前积分余额、累计兑换积分、累计消耗积分、最后更新时间。
- **积分流水（CreditsTransaction）**: 流水 ID、用户 ID、变动类型（兑换/消耗）、变动积分数量、关联兑换码或节点操作 ID、发生时间。
- **节点积分配置（NodeCreditConfig）**: 节点类型、基础积分消耗值、是否启用、最后更新时间；存储于 Convex 数据库，管理员可通过后台动态修改，无需重新部署。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户完成一次兑换码兑换操作（从进入页面到兑换成功）耗时不超过 30 秒。
- **SC-002**: 积分余额在兑换成功后 3 秒内更新显示。
- **SC-003**: 所有需要 LLM 调用的节点按钮 100% 显示积分消耗标签，无遗漏。
- **SC-004**: 积分不足拦截成功率 100%，不存在积分不足仍成功触发 LLM 调用的情况。
- **SC-005**: 同一兑换码重复使用被拦截率 100%，无重复兑换漏洞。
- **SC-006**: 管理员脚本生成 1000 个兑换码的耗时不超过 1 分钟。
- **SC-007**: 生成的兑换码唯一性达 100%，无重复。

## Assumptions

- 积分余额不设上限，用户可累计兑换多个兑换码。
- 积分不可退还，一旦扣减不支持退款（初期简单起见）。
- 兑换码由管理员线下分发，系统不提供在线购买入口（初期）。
- 每个项目节点类型的基础积分消耗值存储于 Convex 数据库的 `NodeCreditConfig` 表中，管理员可动态修改，无需重新部署（原"硬编码或配置文件"方案已废弃）。
- 图片附加积分规则：ceil(图片数量 / 3)，即 1-3 张 = 1 点附加，4-6 张 = 2 点附加，0 张 = 0 点附加。
- Dashboard 侧边栏的「兑换码」入口视觉风格与现有 Setting 界面保持一致。
- 兑换码格式：大写字母+数字组合，固定 16 位，生成和展示时使用 `XXXX-XXXX-XXXX-XXXX` 连字符分组格式，存储时去除连字符以纯 16 位字符串保存。
- 积分扣减时序：先发起 LLM 调用，调用成功后扣减积分；调用失败则不扣减（原"调用失败不退还"假设已废弃）。
- 离线脚本需要具有数据库访问权限，由管理员在服务器或本地有权限的环境下运行。
- 现有用户无初始积分，需通过兑换码获取第一批积分。
